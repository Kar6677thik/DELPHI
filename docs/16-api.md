# 16 — API contract

Base path `/api/v1`. JSON over HTTPS. The OpenAPI 3.1 document is generated by FastAPI and
checked into `backend/openapi.json` (regenerate with `uv run delphi openapi`). CI fails if the
generated file differs from the committed one (schema-first discipline, EFG §7). Every operation
documents its error body as a `default` response of `application/problem+json` with the
`Problem` schema (§1). Frontend types are generated from it with
`openapi-typescript` into `frontend/src/api/schema.d.ts`, and CI checks that file too. The api also serves the document at `GET /api/v1/openapi.json` without signing in: the same
file is in this public repository, so it reveals nothing more (#127).

## 1. Conventions

| Topic | Rule |
|---|---|
| Auth | Session cookie `delphi_session` (httpOnly, Secure, SameSite=Strict). Every endpoint except `/health`, `/ready` and `/auth/login` requires a session |
| CSRF | Mutating requests (any method but GET/HEAD/OPTIONS under `/api/`) MUST carry the header `X-Delphi-Csrf: 1` and an `Origin` equal to the configured public origin (`DELPHI_PUBLIC_ORIGIN`; the request's own origin when unset); otherwise `403 CSRF_REJECTED`. This includes `/auth/login` (login CSRF). The check runs before routing, so it also answers unknown paths |
| IDs | UUIDv7 strings |
| Money | `*_paise` integers. The API never sends float rupees |
| Probabilities | `{hypothesis_key: float}`, 6 decimals |
| Time | RFC 3339 UTC strings (`…Z`) |
| Pagination | Keyset: `?limit=50&cursor=<opaque>`; response `{items, next_cursor}`. Max limit 200 |
| Idempotency | `Idempotency-Key` header (UUID) REQUIRED on: create Guardian session, probe response, evidence request, disposition, chase operation, lien approvals, job creation. The same key and same body returns the stored response, with header `Idempotent-Replayed: true`; the same key with a different body (or endpoint) returns `409 IDEMPOTENCY_CONFLICT`. Bodies are compared after canonicalising JSON (sorted keys, no whitespace). Keys are per user. A missing or non-UUID key is `422 VALIDATION_FAILED`. The response is stored in the same transaction as the request's changes, and concurrent requests with one key are serialised, so the work runs once. An error response is not stored. Keys are kept 24 h |
| Concurrency | Mutable aggregates return `ETag: "<version>"`. Mutations need `If-Match`; a mismatch returns `412 VERSION_CONFLICT` |
| Errors | RFC 9457 `application/problem+json`: `{type, title, status, detail, code, instance, request_id, errors?: [{path, code, message}]}` |
| Request id | `X-Request-Id` is accepted or generated, and echoed in the response and the logs |
| Rate limits | Login: 5 failures / 15 min per (username, IP) → `429 RATE_LIMITED`. Global: 20 req/s per session, token bucket with burst 40 (`DELPHI_RATE_LIMIT_PER_S`, `DELPHI_RATE_LIMIT_BURST`) → `429 RATE_LIMITED` with `Retry-After`. Every `/api/` request takes a token except `/health` and `/ready`; a caller without a session is keyed by its client address. Every request also takes a token from its client address's own bucket, 100 req/s with burst 200 (`DELPHI_RATE_LIMIT_ADDRESS_PER_S`, `DELPHI_RATE_LIMIT_ADDRESS_BURST`), so sending a new session cookie each time does not escape the limit; and `POST /auth/login` takes one from the address's sign-in bucket, 1/s with burst 10 (`DELPHI_LOGIN_RATE_PER_S`, `DELPHI_LOGIN_RATE_BURST`), since each attempt costs an Argon2 hash (#127). The SSE stream is one request. In process memory, like the login throttle (one api replica) |

### Error codes (stable)

`VALIDATION_FAILED` (422), `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `CSRF_REJECTED` (403),
`NOT_FOUND` (404), `IDEMPOTENCY_CONFLICT` (409), `INVALID_STATE_TRANSITION` (409),
`VERSION_CONFLICT` (412), `RATE_LIMITED` (429), `INVALID_CLIENT_SIGNALS` (400),
`PROBE_NOT_AWAITING` (409), `KB_VALIDATION_FAILED` (422), `FOUR_EYES_REQUIRED` (409),
`SHADOW_INSUFFICIENT` (409), `KB_STALE_PARENT` (409), `JOB_ALREADY_RUNNING` (409),
`NOT_INITIALISED` (503: dataset or models not ready yet; returned by Guardian, Navigator,
Chase and Scout write endpoints), `INTERNAL` (500).

`GuardianSessionView`:

```
{ id, payment: {...}, status, kb_version_id, prior: {probs, p_model, anomaly_percentile, open_mass,
  top_features: [{name, value, contribution}]}, posterior: {...}, decision, terminal_reason,
  risk_by_decision: {...}, unexplained: bool, started_at, decided_at,
  probe_runs: [ { id, seq, probe_key, mode, status, selected_by, propensity, outcome,

```

`baselines` (doc 08 §6, doc 22 §2) are computed when the prior is built, from what the bank knew
at initiation, and stored in `guardian_sessions.baseline_decisions`. B1 is `RELEASE`,
`HOLD_FOR_REVIEW` or `DECLINE`. B2 is `RELEASE`, `HOLD_FOR_REVIEW`, or `OTP_STEP_UP` in its
middle band: B2 releases only if the OTP passes, which the bank cannot know without asking (the
monitor's "OTP would pass" line). Risks are whole paise; probabilities have 6 decimals.

**M4 stub (#97):** `GET /cases` and `GET /cases/{id}` are served; the other case routes come with
#103. The list filters `status`, `type` and `protocol` and sorts by `sla_due_at` (soonest first)
or `opened_at` (newest first), and by `expected_loss` (largest first, #208: the recommended
decision's risk; a case stored without one sorts last); `campaign_id` and `sla_breached` filters
come with campaigns. A cursor is tied to its sort order. `CaseView` holds the
opening fields (posterior, prior components, leading hypothesis, amount, SLA and `sla_breached`,
`version` with `ETag`); `recommended_decision` and `risk_by_decision` are stored when the case opens and after each evidence record, and again at disposition (#208).

## 3. Server-Sent Events

`GET /api/v1/events/stream` with `Accept: text/event-stream`. Query `topics` (comma-separated,
default all) selects event types by prefix:
- `guardian` → `guardian.*`
- `cases` → `case.*`, `evidence.*`, `campaign.*`
- `chase` → `chase.*`
- `jobs` → `job.*`
- `scout` → `scout.*`
- `kb` → `kb.*`
- `sensing` → `artifact.*`
- `sim` → `sim.*`

An unknown topic, or a `Last-Event-ID` that is not an event id, is `422 VALIDATION_FAILED`.
The stream needs the `view` permission. Each event:

```
id: <outbox_events.id>
event: <type>
data: {"type": "...", "entity_id": "...", "at": "...", "payload": {...}}
```

Event types: `guardian.session.updated`, `guardian.session.decided`, `case.opened`,
`case.updated`, `evidence.narrative_ready`, `campaign.updated`, `chase.updated`,
`chase.lien.updated`, `job.updated`, `scout.cluster.created`, `kb.version.changed`, `artifact.activated` (a sensing model became
ACTIVE: the api and the worker reload it, docs/13 §7),
`sim.transfer` (demo feed). An `: open` comment is sent as soon as the stream opens (some
proxies hold the response head until the first body bytes), and a heartbeat comment (`: ping`)
every 15 s. Reconnect with
`Last-Event-ID` replays from `outbox_events` (retained 24 h). A client that cannot set the
header (a new `EventSource`, opened after the browser gave up on an HTTP error) passes it as
`?last_event_id=<id>`; the header wins if both are sent. SSE payloads are small: clients
re-fetch the entity via REST.
